1. EXPERIMENT OVERVIEW
======================================================================

This research project investigates how QUIC protocol parameters affect
network performance metrics across different application types. The
experiment systematically varies three QUIC congestion control
parameters and measures six performance metrics for three distinct
traffic patterns.

Research Question:
------------------
How do QUIC protocol parameters (initial congestion window, max ACK
delay, and loss reduction factor) impact performance metrics
(throughput, RTT, jitter, packet loss, connection time) for different
application types (video streaming, file transfer, conference calls)?


======================================================================
2. WHY THIS IS A CONTROLLED EXPERIMENT
======================================================================

This project qualifies as a controlled experiment because it adheres
to the fundamental principles of experimental design:

2.1 Systematic Variable Manipulation
------------------------------------
We deliberately and systematically vary independent variables (QUIC
parameters) while measuring their effect on dependent variables
(performance metrics).

2.2 Variable Control
--------------------
All other factors that could influence results are held constant:
- Network environment (localhost)
- Data generation patterns (deterministic synthesizers)
- Software versions (pinned dependencies)
- Traffic volume per application type (see Section 4)

2.3 Isolation
-------------
Running on localhost eliminates external factors:
- No real network congestion
- No packet loss from network equipment
- No variable latency from geographic distance
- No interference from other network traffic

2.4 Reproducibility
-------------------
The experiment can be reproduced exactly:
- Fixed random seeds in data generation
- Deterministic parameter combinations
- Version-controlled codebase
- Documented methodology

2.5 Exhaustive Parameter Space Exploration
------------------------------------------
Grid search covers ALL combinations (192 total), not a sample,
ensuring complete coverage of the parameter space.

4. APPLICATION TYPES AND TRAFFIC PATTERNS
======================================================================

4.1 Video Streaming
-------------------
Simulates adaptive video playback (e.g., Netflix, YouTube)

Traffic Pattern:
- Frame rate: 30 fps
- I-frames: ~50 KB every 60 frames (keyframes)
- P-frames: ~5 KB (delta frames)
- Timing: Regular intervals (33.3ms between frames)

Optimization Target: Minimize RTT
Rationale: Lower latency enables faster quality adaptation and
           reduces buffering during playback start.


4.2 File Transfer
-----------------
Simulates bulk data transfer (e.g., downloads, backups)

Traffic Pattern:
- Chunk size: 64 KB
- Total size: 10 MB
- Timing: No delay between chunks (maximum throughput)
- Pattern: Continuous stream until complete
- Duration: Variable (~0.2-0.5s depending on throughput achieved)

NOTE: Unlike video and conference, file transfer does NOT use a fixed
duration. It sends 10 MB as fast as possible and completes when done.
This is intentional - real file transfers don't have timing constraints.

Optimization Target: Maximize Throughput
Rationale: Faster transfer = less time waiting for downloads.


4.3 Conference Call
-------------------
Simulates real-time audio/video communication (e.g., Zoom, Teams)

Traffic Pattern:
- Packet interval: 20ms (50 packets/second)
- Packet size: ~320 bytes (based on 128kbps audio)
- Timing: Strict regular intervals

Optimization Target: Minimize Jitter
Rationale: Consistent packet timing is critical for smooth
           audio/video playback without stuttering.

5. METHODOLOGY
======================================================================

5.1 Parameter Application
-------------------------
QUIC parameters are applied using two techniques:

1. Official API (max_ack_delay):
   Set via QuicConfiguration.max_ack_delay before connection.

2. Runtime Patching (initial_cw, loss_factor):
   Modify aioquic.quic.congestion.cubic module constants at runtime.
   Values are restored after each simulation.

   See: params_tuning_report.txt for detailed explanation.


5.2 Execution Flow
------------------
For each of the 192 parameter combinations:

    1. Patch aioquic with test parameters
    2. Start QUIC server on localhost:4433
    3. Connect QUIC client
    4. Open 3 streams
    5. Generate synthetic traffic:
       - Video/Conference: Run for 10 seconds (timing-controlled)
       - File Transfer: Send 10 MB as fast as possible (size-controlled)
    6. Collect metrics during transmission
    7. Stop client and server
    8. Restore original aioquic parameters
    9. Export metrics to CSV file
    10. Proceed to next combination


5.3 Resumability
----------------
The experiment supports crash recovery:
- Completed simulations are detected by existing CSV files
- On restart, only pending combinations are executed
- No duplicate measurements


5.4 Output Format
-----------------
Each simulation produces a CSV file:
    <app_type>_<initial_cw>_<max_ack_delay>_<loss_factor>.csv

Example: video_streaming_36000_0.025_0.5.csv

CSV columns:
- initial_congestion_window
- max_ack_delay
- loss_reduction_factor
- throughput
- rtt
- latency (calculated as RTT/2)
- jitter
- packet_loss_rate
- connection_establishment_time


======================================================================
6. EXPERIMENTAL CONTROLS
======================================================================

6.1 Ensuring Parameter Isolation
--------------------------------
Each simulation runs with a fresh parameter set:

    try:
        apply_parameters()      # Set test values
        run_simulation()
    finally:
        restore_parameters()    # Always restore defaults

The `finally` block guarantees restoration even if errors occur.


6.2 Sequential Execution
------------------------
Simulations run sequentially (not in parallel) to prevent:
- Parameter interference between concurrent tests
- Resource contention affecting measurements
- Race conditions in metric collection


6.3 Warm-up Period
------------------
A 100ms delay between server start and client connection ensures
the server is fully ready before the test begins.


======================================================================
7. LIMITATIONS AND CAVEATS
======================================================================

This experiment has known limitations that should be considered
when interpreting results:

7.1 Localhost Environment
-------------------------
- No real network latency (RTT is artificially low: 2-7ms)
- No actual packet loss (0% in all tests)
- No bandwidth constraints
- No competing network traffic

Implication: Results show parameter effects in ideal conditions,
not real-world network behavior.


7.2 Single Machine
------------------
- Client and server share CPU/memory resources
- System load variations may affect timing measurements
- No geographic distance simulation

Implication: Connection establishment times and RTT values are
not representative of internet-scale deployments.


7.3 Runtime Patching
--------------------
- Modifies library internals (not public API)
- May break with aioquic updates
- Affects global state

Implication: Approach is valid for research but not suitable
for production systems.


7.4 Synthetic Traffic
---------------------
- Traffic patterns are deterministic approximations
- Real applications have more variable behavior
- No application-layer retransmissions or adaptations

Implication: Results reflect QUIC-level behavior, not full
application stack performance.

9. EXPECTED OUTCOMES
======================================================================

Based on QUIC protocol behavior, we expect:

9.1 Initial Congestion Window
-----------------------------
- Larger ICW → Higher initial throughput
- Larger ICW → Potentially higher RTT during ramp-up
- Most impact on short transfers

9.2 Max ACK Delay
-----------------
- Lower delay → Lower RTT (faster acknowledgments)
- Lower delay → Higher overhead (more ACK packets)
- Higher delay → Better throughput (batched ACKs)

9.3 Loss Reduction Factor
-------------------------
- Lower factor (0.4) → Aggressive recovery, faster ramp-down
- Higher factor (0.7) → Conservative, maintains higher window
- Impact depends on loss frequency (minimal on localhost)

11. CONCLUSION
======================================================================

This controlled experiment provides a systematic exploration of QUIC
parameter effects in an isolated environment. While the localhost
setting limits real-world applicability, it enables precise
measurement of parameter impacts without network variability.

The results can inform:
- Initial parameter selection for specific application types
- Understanding of parameter sensitivity
- Hypotheses for real-network testing

For production deployment, findings should be validated with:
- Real network conditions
- Varied latency and bandwidth
- Actual packet loss scenarios
- Geographic distribution
